# 集中检索与索引更新草案

状态：记录已经讨论的方向，供后续审阅。模型、存储引擎、切片参数、部署方式、API 与鉴权尚未定案。本章不是开发或部署授权。

## 职责边界

Git 仓库保存正式文件及历史，Gitea 管理仓库与协作。独立检索服务集中保存关键词倒排索引、向量索引、切片与来源映射；全部是可重建的派生数据，不随普通资料反复提交到仓库。

本地 `scripts/search.py` 拟作为薄 HTTPS 客户端。正常集中检索不要求每个 Agent 下载模型、向量库或完整仓库，工作 Agent 也不直接新增、删除或修补索引条目。

不同知识库可以有不同的写入与归档规范；检索服务只共享文件读取、元数据理解、检索与来源定位能力，不统一改写各库的业务规则。

## 查询与结果

建议支持关键词、语义及混合三种模式。请求可以给出一个或多个仓库范围、多个关键词、一段自然语言查询和结果数量；实际接口字段、默认值与分页以后确定。

关键词检索和向量检索分别产生候选排名，初步采用 RRF 合并排名，不直接相加量纲不同的原始分数。采用该算法不意味着必须选用某个大型搜索产品。参见 [RRF 原理](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。

结果至少应定位到仓库、文件路径、标题、片段位置和索引对应的 Git 提交。尽量返回可打开的原文链接，历史证据链接固定到对应提交；最新主分支链接可另附，不混淆两者。

检索服务第一阶段只负责召回，不额外生成一篇无来源答案。调用方 Agent 读取原文后自行完成任务；summary 是粗略定位线索，不代替全文。

## 模型与多模态

- 自托管处理嵌入，候选方向为 CPU 推理；具体模型、内存、速度和中文效果以后实测。
- 查询时同样需要对自然语言查询计算向量，并使用与文档向量兼容的空间与配置。
- 图文相似性检索与图片内文字检索是不同需求；多模态 embedding 与 OCR 是否组合、如何处理图片和其他附件，留待单独设计。
- 不承诺几 MB 或约 300 MB 的模型必然满足中文、多模态和召回质量要求。
- 下载模型权重不等于将业务资料上传给模型托管平台；运行时不得隐式调用外部 embedding 或 OCR 服务。
- 若查询结果交给云端 Agent，返回片段仍会进入该 Agent 的上下文；本地 embedding 不等于整个使用链路完全不外传。

语义查询与文档编码关系可参考 [Sentence Transformers 语义检索说明](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)。

## 主分支更新流程

```text
正式资料进入主分支
        ↓
自托管 Gitea Action 通知仓库与目标提交
        ↓
检索服务按仓库排队，取得目标快照
        ↓
读取文件、切片、复用已知向量、计算新增向量
        ↓
生成完整候选索引并校验
        ↓
原子发布新索引，记录 indexed_commit
```

可从“扫描目标快照的全部合规文件，再按切片去重”起步，不必一开始实现复杂 Git 增量解析。生成 INDEX、工具和 Skill 等是否进入搜索由明确的收录规则决定，不能不加区分地把仓库所有文件都当正文；生成 INDEX 默认排除。

### 切片缓存和删除

- 缓存键包含实际编码输入的内容哈希，以及模型、预处理和切片配置版本。
- 命中兼容缓存则复用向量，未命中才计算；换模型或改变输入规则不能误用旧向量。
- 同一内容出现在不同位置时可以复用计算结果，但保留各自的仓库、路径、权限与引用关系。
- 当前快照不再包含的内容应从该仓库的活动索引移除；移除一条引用不等于删除其他文档仍在使用的共享缓存。
- 原文与 Git 历史不因切片、去重或索引删除被修改。

### 多提交排队

每仓库最多一个运行中的构建，并只保留一个最新待处理目标：

```text
A 构建中
收到 B → 待处理 B
收到 C → 用 C 替换待处理 B
A 完成 → 直接构建 C
```

日常搜索跟随当前主分支，不要求每个中间提交都生成一份可搜索快照。可以短暂合并突发通知，但不能通过无限重置等待时间使持续提交的仓库永远不更新，也不能每次来新提交就取消正在进行的计算。

通知重复到达或乱序时，应重新核对当前主分支目标，而不是按消息到达顺序倒退。正常单仓串行发布避免旧任务覆盖新结果；失败保留上一份完整索引及明确失败状态，不发布半成品。

`indexed_commit` 仅在成功发布后更新。客户端能够知道当前索引的新旧状态；索引构建失败不能被解释为“仓库没有内容”。

## 权限方向与未决问题

建议的原则是：搜索不得扩大调用方在 Gitea 的仓库内容读取权限。索引是否已经存在，不能决定调用方是否可以看到其内容。

```text
实际可搜索范围
= 已接入的仓库
∩ 调用身份及凭据可读取内容的仓库
∩ 本次请求指定的范围
```

建索引的后台只读身份与查询者身份分开：后台为了建库可能读得到多个仓库，不能拿后台权限替查询者放行。过滤应覆盖关键词、向量、混合排序和结果输出，包括标题、摘要、计数与片段，不能只在最后隐藏链接。

Gitea 已提供仓库 Code 权限、API Token 和 OAuth2 能力，可作为后续鉴权设计依据，但不会自动保护外部检索数据库。参见 [仓库权限](https://docs.gitea.com/usage/access-control/permissions/)、[API 鉴权](https://docs.gitea.com/development/api-usage/)和 [OAuth2](https://docs.gitea.com/development/oauth2-provider/)。

以下仍待讨论，不把上一轮示意流程固化为接口：

- 使用专用只读 Token 委托、OAuth2，还是其他与 Gitea 关联的身份机制；
- 服务是否保存凭据、如何降低其授权范围及轮换；
- 如何准确核对 Code 读取权限与凭据自身限制；
- 权限缓存、撤销延迟和 Gitea 暂时不可用时的行为；
- 跨仓库查询范围发现、私有仓库名称保护，以及仓库迁移或删除后的处理。

无论选择哪种机制，都不能在鉴权失败时退回后台全库权限，也不能仅相信客户端提交的仓库列表。共用一个账号不自动产生多个隔离身份；Skill 规则不是服务端授权边界。

## 后续验收重点

实施时优先验证实际使用：普通关键词能找到刚提交内容，中文语义查询有可解释来源，重复切片不重复计算，删除后活动索引不残留，多次提交最终追上最新主分支，失败不破坏上一份索引，以及不同读取权限不会串库。

这些是后续验证目标，不要求本轮建立测试矩阵、部署模型或创建自动化任务。具体鉴权和多模态方案应在实施前再次审阅。

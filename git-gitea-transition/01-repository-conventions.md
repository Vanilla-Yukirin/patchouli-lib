# 知识库目录与文档元数据

本规范描述后续 Git 知识库。它不要求立即改写现有资料，也不改变当前 PatchouliLib 存储模型。

## 目录组织

一个仓库对应一个用途明确的知识库。根目录的资料子文件夹称为分区；工具、配置和 Skill 目录不属于分区。

```text
archive/
├── README.md
├── AGENTS.md
├── INDEX.md                         # 程序生成的分区总览
├── skills/
│   ├── patchouli-lib-archive/
│   │   └── SKILL.md
│   └── patchouli-lib-archive-search/
│       └── SKILL.md
├── scripts/                         # 仓库共享 CLI，未来实现
├── .gitea/                          # 未来的自动检查和索引通知
└── project-notes/                   # 一个资料分区
    ├── README.md
    ├── INDEX.md                     # 程序生成的本分区文档表
    ├── 202610241030-archive-release-review.md
    └── 202610241030-archive-release-review/
        ├── screenshot.png
        ├── results.json
        ├── supplementary-notes.md
        └── scripts/
            └── inspect.py
```

以上时间戳采用下文的候选格式，仅用于展示结构。

### 主文档与附件

- 分区内每份资料必须有一个直接放置的 `.md` 主文档。
- 附件目录与主文档去掉 `.md` 后完全同名；无附件时不必创建空目录。
- 附件目录可以包含任意类型的资料及子目录，包括额外 Markdown、PDF、数据、图片、音视频和脚本。
- 附件中的 Markdown 不自动升级为另一篇主文档，不作为分区 INDEX 的独立条目。
- 正文通过相对链接引用附件，例如 `./202610241030-archive-release-review/screenshot.png`。
- 上传附件不等于执行附件；发现脚本或宏不自动运行。凭据和不应共享的数据仍不能入库。
- 不再额外设置“主文档选择器”：同级 `.md` 与同名附件目录已经确定归属。

## README 的职责

### 根 README

说明知识库用途、资料组织、使用入口和适用规则。Archive 的类型、命名、元数据和操作检查要求应在它与根 `AGENTS.md` 中清楚列出或引用；两者不能给出不同版本的规则。

### 分区 README

建议采用“一个一级标题加一段简短说明”描述：

- 分区名称的含义；
- 接收哪些资料；
- 不接收哪些资料；
- 与相似分区如何划界，必要时用分区名称指明去向。

分区 README 不包含相对链接或相对图片地址，也不把链接藏进引用式定义或 HTML 属性。一般也不需要外部链接。导航由生成的 INDEX 负责，详细指令放相应 Skill，不在分区说明中塞入冗长操作手册。

分区 README 的用途段落就是根 INDEX 的摘要来源，不另设一份需要人工维护的“分区简介数据库”。根 README 和正文不受“分区 README 禁止相对链接”这一局部限制。

## 主文档元数据

每篇受规范管理的主文档使用 UTF-8 Markdown，并以 YAML front matter 开头：

```markdown
---
summary: >-
  说明本篇资料涉及的事项、核心结果和适用范围。
  可以用一段话保留重要背景与未解决问题，方便查找时判断相关性。
tags:
  - release
  - operations
created_at: "2026-10-24T02:30:00Z"
updated_at: "2026-10-24T03:10:00Z"
---

# 本篇资料的标题

正文从这里开始。
```

示例时间不是运行时默认值。最终字段名沿用此前确认的 `tags`，不是另建 `text` 字段；正文已经承担文档文本。

| 字段或位置 | 规则 |
| --- | --- |
| 第一个正文一级标题 | 作为显示标题；不维护重复 `title` 元数据。应按 Markdown 解析标题，不能误取代码块里的 `#` |
| `summary` | 非空字符串，可以是一段话；概括内容、结果与边界，不替代全文 |
| `tags` | 字符串列表，允许空列表；去掉重复项，不写成逗号拼接的一个字符串 |
| `created_at` | 文档首次创建时间，Agent 维护，后续编辑保留 |
| `updated_at` | 最近一次正文或实质元数据修改时间，Agent 维护 |

根说明、分区 README、AGENTS、生成 INDEX、Skill 和工具说明有各自职责，不套用 Archive 主文档的文件名与四字段检查；Skill 自己的 front matter 仍遵循 Skill 格式。附件里的 Markdown 也不强制补写主文档元数据。

### 时间语义

- 文档时间独立于 Git commit 时间。提交时间只承担版本追溯，不代填文档创建或更新时间。
- Agent 从实际系统时钟取得时间，以带明确时区的 ISO 8601 值写入；示例使用 UTC，不要求把运行环境改成某个时区。
- 不凭模型估算当前时间，不用复制后的文件修改时间冒充创建时间。
- 生成 INDEX、重算向量或仅移动文件，不自动刷新正文的 `updated_at`。
- 校验日期能解析、含时区，且更新时间不早于创建时间；无需对正常时钟偏差建立复杂审计系统。
- 新文档写入上述字段；旧资料若时间不明，后续迁移规范应保留未知及来源，不得为了通过检查虚构时间。

## Archive 专用文件名规范

以下只适用于组织内 Archive 仓库各分区的主文档，不约束其他知识库，也不约束附件文件名。

```text
{timestamp}-{type}-{english-slug}.md
```

- 主文档文件名使用 ASCII 英文字母、数字和连字符；slug 使用小写英文短语或字母数字标识，单词用 `-` 分隔。
- 时间戳必须位于开头，长度固定，并通过真实日历日期与时间校验；仅匹配数字正则不够。
- 文件名中的时间戳创建后保持稳定，不随 `updated_at` 改动。
- 主标题和正文可以使用中文等自然语言，不因文件名规则被限制为英文。
- 同名冲突时调整 slug，不覆盖已有资料，也不伪造创建时间。
- 类型扩展需要更新仓库规则和校验器，不由 Agent 临时发明新值。

| `type` | 用途 |
| --- | --- |
| `archive` | 工作、讨论、实施和验收结果的归档记录 |
| `todo` | 计划、待办事项及后续跟进说明 |
| `file` | 主要目的是保存附件文件；MD 作为这批文件的说明、来源和阅读入口 |

`file` 主文档也要有标题、摘要、标签和时间，并说明附件内容；它不是可以省略的空占位文件。

### 时间戳候选格式

**待确认：** 用户要求固定长度和合法时间，但没有最终指定精度与编码时区。

候选为 `YYYYMMDDHHmm`，12 位、精确到分钟。若采纳，形状检查为：

```regex
^[0-9]{12}-(archive|todo|file)-[a-z0-9]+(?:-[a-z0-9]+)*\.md$
```

随后必须单独解析月份、日期、小时和分钟。编码时区应由未来仓库规则明确指定，并由程序正常转换；不得暗中使用某台机器的本地时区或手工加减固定小时。精度和时区定案前，不实施批量改名或命名校验部署。

## 规则适用边界

新增分区时先阅读已有分区说明，确认用途不重复，再创建分区 README。不需要为了一个资料包创建新分区：主文档和附件目录已经能容纳一批相关文件。

旧记录保留，禁止为了让新目录看起来整齐而覆盖旧稿、改写 Git 历史或自动丢弃附件。任何实际迁移另行决定。

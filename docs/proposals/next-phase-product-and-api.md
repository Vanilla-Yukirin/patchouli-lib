# 下一阶段管理后台、内容模型与 Agent 接入设计

- 状态：**产品目标已由维护者确认；接口、存储与迁移方案仍为提案中（Proposed）**。
- 范围：多知识库管理、多文件 Page、设备凭据、内容活动、真实搜索和 AI 原生接入。
- 本文只定义目标和待验证的实施约束，不表示相关程序已经发布，也不授权真实数据迁移、
  私有部署或更改既有提案的状态。

## 2. 内容层级与命名

```text
Library（一个逻辑知识空间，可有多个）
└── Section（长期使用的大类）
    └── Book（一组相关 Page；一本 Book 只有一个 Page 也合法）
        └── Page（一个可独立寻址的内容单元）
            └── Revision（该 Page 在某次写入后的不可变完整快照）
```

一个部署可以容纳多个 Library，例如对话归档和公共资料分别成库；它们共享同一服务和
数据库，因此只是逻辑分隔，不是物理隔离。Section 可表示资料来源或长期主题；Book
可表示一段项目工作、一期视频或一个具体事件；Page 可表示该 Book 中的一篇摘要或
一份资料。**一 Book 一 Page 完全正常**，不能为了满足目录外形强行增加空 Page。
Book 也不必须为每份新 Page 单独创建；管理界面应允许复用现有 Book。

用于展示的 Library、Section、Book 和 Page 名称可以是中文或英文。Page 标题不是
路径或唯一身份；稳定 Page ID 由服务生成，后续更名、移动 Book 或校正声明时间时
仍应保持不变。当前 `page-v1` ID 包含首次创建时的时间和标题派生片段；一旦允许
校正声明时间，ID 中的旧片段只能视为历史标识，检索和排序必须使用可校正的声明时间
字段，不能从 ID 反推当前时间。ID 格式是否改版属于独立兼容性决定。

Tag 是跨层级的多对多标记和检索投影，不替代 Library／Section／Book 归属，也不是
授权边界。现有设计中的 Shelf 是另一种已保存的 Book 视图，不能把 Tag 管理隐式
实现为 Shelf。Tag 和 Shelf 的关联及后者的产品必要性可在后续单独决定。

本开发分支已加入 Tag 的持久化底座：显示名采用 Unicode NFC，匹配键采用
NFC→casefold→NFC，同一 Library 内唯一；关联记录用 Library 与 Page 的准确身份
约束。当前开发分支还提供受保护的 Tag 创建、列举、Page 关联与按 Tag 列 Page
接口，但仍沿用旧 Section 授权；Tag 与关键词、时间的组合搜索尚未实现。这些切片
不表示本提案其余内容已获接受。

## 3. Page 是平面多文件内容单元

### 3.1 文件模型

Page 不再被限定为一份 `.md`。其当前 Revision 可以只含一份 Markdown，也可以含
Markdown、图片、JSON、脚本、表格、演示文稿或其他允许的文件；还可以完全没有
Markdown，例如只有一份演示文稿。这里的「文件」是 Page 内容本身，**没有主文件／
附件的父子关系**。Book 管理 Page，Page 管理它的一组文件，Revision 保存某一时刻
这组文件的完整状态。这只是类似小型版本仓库的产品比喻，不要求每个 Page 真正创建
Git 仓库或暴露 Git 命令。

Page 内只有一个平面文件名空间，不接受子目录、绝对路径、`..`、路径分隔符、符号
链接或重名文件。文件名可以使用受支持的 Unicode 字符，但服务必须统一规范化并拒绝
跨平台含糊的名字；原始显示名与规范化键是否分存须由存储提案确定。Markdown 若引用
同一 Page 的图片或其他文件，应使用受约束的相对引用；渲染器只解析当前 Revision
文件清单中的同级文件，绝不借此访问服务器文件系统或其他 Page。跨 Page 引用仍通过
明确的 Page／Revision 引用机制完成。

文件类型不应只凭扩展名判定；响应的 MIME、下载名、内联预览与可执行内容隔离必须
分别设计。最初只需可靠保存、下载和校验允许的文件；视频播放、表格在线编辑、脚本
执行、病毒扫描或内容理解不因「可保存文件」而自动成为已实现能力。单文件、单 Page、
单次请求和整库的大小限制，以及允许的文件类型，需在实施前用真实容量和备份成本
确定并公开。
只有文件名、标题、Tag、说明及 Page 内可提取的文字可进入首版全文索引；保存原始
PPTX、图片或视频不等于已经能搜索它们的内部内容。若后续需要 OCR、转录或文档解析，
必须分别定义派生文本、来源、版本和资源预算。

### 3.2 Revision 与同内容写入

每个 Revision 是该 Page 文件清单和各文件字节的不可变完整快照。新增、删除、改名
或更改其中任何文件都会形成新的内容快照；恢复旧版本是创建一个内容等于旧快照的
**新** Revision，而不是改写历史指针。实现可在内部对相同文件字节去重存储，但对外
仍必须能按 Revision 准确还原整组文件。二进制数据、文件清单、当前指针、派生索引、
审计和成功幂等记录的提交边界应作为一个事务设计，不能返回成功后缺失某个文件。
如果选择恢复的旧快照与当前快照完全相同，则返回「内容未变化」，不另建 Revision；
只有实际把当前内容改回旧快照时，才通过新 Revision 记录这次恢复。

内容相同的判定不能仅比较某一份 Markdown 的哈希。多文件 Page 应比较规范化的
文件名集合及每个文件的内容哈希；同一组文件名和字节再次提交到**同一个 Page**时，
返回明确的「内容未变化」结果和当前准确引用，不新增 Revision。同样的字节上传到
另一个 Book 或另一个 Page 是独立内容，不能用全库哈希合并。标题、Tag、来源或声明
时间等元数据如果变化，应作为可审计的元数据修改处理；正文未变本身不应凭空制造
一个内容 Revision。具体哈希规范、编码、校验和错误码需要公开接口提案固定。

### 3.3 写入、读取与本地文件

Agent 可先将准备上传的正文和其他文件写入本机，再调用标准 HTTP 接口；不要求用户
事先逐篇预览，也不要求为每个 Page 生成一套额外的「待上传包」。接口应明确选择目标
Library、Section 和 Book，区分「新建 Page」与「更新既有 Page」。更新优先使用服务
返回并可在本地记下的 Page ID 和当前 Revision／ETag；标题或本地路径不能作为唯一
身份。找不到本地记录时可以进行受权限约束的搜索和人工消歧，不得猜测目标 Page。

一次上传在结果丢失后重试，必须重放同一幂等身份和完全相同的目标、元数据、文件
清单及文件字节；改变任何一项都应开始新操作。成功响应后，Agent 应读取**本次目标
Page 的准确 Revision**并核对文件清单和哈希。全库找到相同哈希只证明某处有相同
字节，不证明本次 Page 上传成功。只有 Agent 为这次上传新建的临时本地副本才能在
成功核验后清理；用户原本已有的源文件绝不自动删除。保存 Page ID 的轻量本地映射
可以提高后续更新可靠性，但不应成为访问服务的强制前提。

现有 Archive 专用 `metadata`＋`content` 上传接口和客户端仍应在过渡期保持可用。
新增多文件协议的原子性、流式处理、表单或其他传输格式、旧 Page 到平面文件清单的
映射，以及回退路径需要专门的接口与迁移审查，不能在本文直接固定为某个新 URL。

## 4. 声明时间、服务器时间与软删除

Page 的**声明发生时间**表示内容实际对应的工作、事件或资料时间，不等于服务器接收
时间，也不等于最后修改时间。搜索的时间过滤默认使用声明发生时间。另保留服务器
创建和更新时间用于审计、排序备选项及排障。上传时提供有效声明时间应原样保存；
缺失时可以服务器当前 UTC 时间代填，同时在结构化响应中明确标注代填来源和警告，
提醒调用方可再校正。**提供了但格式或取值无效的时间应拒绝并要求修正**，不能静默
用当前时间污染历史排序。服务端还应提供受授权保护的声明时间校正操作，记录旧值、
新值和操作者；校正后不改变稳定 Page ID 或已有 Revision 正文。
旧 `page-v1` 存储校验要求 ID 中的初始时间分量与 `occurred_at` 一致。本开发分支
已经在存储层解耦「不可变的初始 ID 时间分量」与「可更正的声明时间」，并增加更正
审计及备份校验；受授权保护的公开更正接口也已在本开发分支实现，详见
[Page 版本与历史](../03-page-revision-and-history.md)。创建 Archive Page 的缺省时间
代填及创建响应中的结构化警告也已在本开发分支实现；普通读取不另存代填来源。这些
切片不代表本提案已获接受、分支已合并或服务已部署。

时间筛选应允许只给起点、只给终点或两者都给，而不是要求调用方填写「极大时间」。
建议定义 UTC 半开区间 `[起点, 终点)`；公开 API 的数字时间戳单位须在接口提案中
精确指定，并在浏览器侧做时区转换。跨时区输入、边界值及代填时间都需要测试。

普通删除以 Page 为单位进入回收站：默认列表、读取和搜索不再返回该 Page，但其全部
历史 Revision 和文件仍随 Page 保留。恢复后恢复同一个 Page 身份、历史与引用；
误删不依赖人工直接修改数据库。后续可以提供独立、严格授权的永久清除流程，但它
不是普通删除，也不能假定备份立刻同步清除。Agent 持有相应写权限时可执行普通创建、
修改、移动和软删除，不设置每次写入都到网页批准的工作流；所有成功变更必须审计。

## 5. 单人管理入口、设备 Token 与授权

目标管理后台只面向一个维护者。首次打开且尚未设置管理身份时，引导建立一个足够长
的管理 Token；登录页使用该 Token，不要求传统用户名。管理身份和普通 Agent／设备
身份必须分开，管理 Token 不应在普通内容 API 中代替设备 Token。现有部署仍使用
密码校验值、签名会话 Cookie 和 CSRF；切换登录方式是未来迁移，不是本文提交后的
即时行为。现有网页密码只负责建立管理会话；签发或吊销 Agent 凭据时，操作者还须
为该次操作提交独立的 operator Token。管理 Token 可在数据库中保存不可逆校验值，
但它是否接替现有 operator Token 的管理权限，及相应的审计主体、授权边界、遗失
恢复和旧登录方式的兼容期，都需要独立安全设计，不得只改登录表单就隐去第二道校验。
尤其不能仅以「数据库尚无管理 Token」为条件向任意远端浏览器开放首次注册：若服务
已经有公开入口，未经保护的初始化页会被抢先占用。首次设置必须有本机操作、一次性
带外证明或等效的部署侧限制；具体方式须在启用新登录前验证。新登录仍应保留短期
HttpOnly、SameSite 会话 Cookie、同源检查和 CSRF 防护，不把管理 Token 放进 Cookie；
管理 Token 轮换或本机恢复后，还须让既有会话及时失效，不能只等 Cookie 自然到期。

管理后台可创建、命名、描述、查看、轮换和吊销 Agent／设备身份。每个身份默认
一份活动 Token；界面默认仅显示首尾各约四个字符，点击眼睛可受保护地显示完整值，
点击复制可再次取得该值。未请求显示时，普通详情页不应预埋完整 Token；显示和复制
应要求有效管理会话、同源与 CSRF 校验，并确定是否还需近期重新验证管理身份，
留下不含凭据的审计记录。响应必须禁止缓存；明文不应进入 URL、日志、受跟踪配置、
管理会话或浏览器持久存储。浏览器自身的密码保存能力可以由使用者选择，但不应作为
服务端保存或恢复 Token 的方案；如需少量自有脚本实现眼睛和复制，也应保持严格的
内容安全策略，不引入第三方脚本或宽松的内联脚本例外。

当前系统只存不可逆校验值、只在签发时显示一次；要实现重复显示，必须另行设计与
校验值并存的可恢复密文、独立于数据库备份的解密材料、密钥版本和轮换、访问控制及
恢复后的失败关闭行为。不得直接把明文 Token 加到表中，也不能让密钥丢失时自动生成
新密钥并假装旧密文仍可解开。现有实验性备份包含数据库文件和清单，不包含解密材料；
恢复到新的空目标也不等于允许重新启用其中的历史凭据。密文恢复能力、独立密钥的
保管和恢复演练，以及旧备份恢复后可能重新出现已吊销凭据的处理，均需先明确。
既有 Token 因从未存储可恢复明文，迁移后也无法「补出」完整值；需保持旧 Token
直到正常到期／吊销，或让管理员轮换签发新格式。可重复复制不等于永不过期；到期、
轮换和吊销仍应清晰展示。当前身份可以签发多枚凭据；「默认一份活动 Token」如何
处理这些旧凭据，也应采用不悄然吊销、不扩大权限的迁移规则。

一枚设备 Token 可授权多个 Library。授权粒度为每个 Library 的 `read` 和 `write`，
不再按 Section、Book、Page 或 Tag 划分；`write` 的读前置需求及两个开关的组合应在
接口契约中明确。新 Library 默认不自动授予已有 Token；管理员可显式为多个 Library
开启读或写。服务在检索、文件下载、写入和索引候选计算前实施同一授权边界，不能只
在结果返回时过滤。当前单 Library＋Section grant 的旧 Token 不得在迁移时悄然扩大
为所有 Library 可读写；需要保留旧语义直到轮换，或由管理员显式重新签发。

已有 `/api/v1/auth/whoami` 可验证 Token，并已增补用于人类识别的调用方名称和说明；
它当前仍返回 Section 授权。下一阶段目标是在不暴露 Token 的前提下返回设备／Agent
身份、凭据状态与有效的 Library 权限。`capabilities` 仍用于识别服务功能；调用方
不能把能通过身份验证误认为具有写入权限。读／写之外的危险管理动作仍只属于管理身份。

## 6. 管理后台信息架构

左侧导航面向日常管理，而不是部署运维：

1. **主页／近况**：按时间展示内容活动。每行说明哪个身份在何时创建、修改、移动、
   删除或恢复了哪一个 Page；身份链接进入对应设备详情，Page 链接进入当前预览或
   指定 Revision。相对时间的悬停信息显示完整绝对时间。
2. **知识库**：自适应网格展示 Library 名称、简介、创建时间及可见内容数量。进入
   Library 后按 Section、Book、Page 浏览；允许一本 Book 只有一个 Page。支持建立
   结构、查看文件清单、预览可安全渲染的类型及浏览历史。
3. **Tag**：列出 Tag、关联 Page 数量和相关内容，允许创建与维护关联。Tag 是筛选
   标签，不决定授权或唯一归属。
4. **设备与 Token**：创建身份、设置各 Library 读／写、查看最近活动和 API 请求、
   掩码／显示／复制／轮换／吊销 Token。
5. **接口与 Agent 指南**：只读展示当前 API 能力、示例响应、Skill、MCP 和内置
   指令文本；这些开发者维护的说明不能在管理页面任意改写。
6. **搜索**：为人类提供关键词、Tag、时间和 Library 选择，与 Agent 使用同一底层
   搜索语义；结果按 Page 展示，可进入预览与准确 Revision。
7. **回收站与请求记录**：浏览和恢复已软删除 Page；另按身份、接口、结果及时间查看
   受保护的 API 请求元数据。

内容活动与 API 请求是不同视角：一次成功写入对应一次可追溯的内容变更；一次普通
读取、搜索、拒绝或失败请求也可有请求记录，但不会伪装成内容变更。请求记录应包含
请求 ID、身份、接口类别、状态、耗时和时间等必要元数据，不得存原始 Authorization、
完整正文、搜索词或接入 Token。保留期限、采样及失败路径覆盖需在实现前确定。首页
不应把网络请求洪流混入内容时间线。

当前管理后台不是主机 Shell、Docker 或镜像控制台。增加内容浏览和 Token 页面不应
顺手加入部署、数据库原始查询或任意代码执行能力。

## 7. AI 原生接入与标准 HTTP

管理页面提供一个任何人可阅读和复制的**无密钥接入指令**，可按实际选择的入口生成
正确服务根地址；公开仓库和示例不得写入维护者私有域名、主机或网络拓扑。指令只
负责引导本地 Agent：若无设备 Token，请用户在管理后台创建或复制；随后由 Agent
展示适用于本机系统的交互式输入方法，让用户在本机终端或受保护的本地机密存储中
填写。**不得要求用户把 Token 发到模型聊天、提示词或远端模型 API，也不得把它作为
Shell 命令行参数写进历史记录。**「一键复制 Token」是页面上的独立受保护动作，
不是把 Token 嵌入公开指令。

持有 Token 后，Agent 先调用身份与能力接口，确认实际身份和权限，再访问需要
Token 的 Skill 下载入口，下载 `SKILL.md` 与清单列出的其他文件，核对版本和摘要，
安装到当前 Agent 环境支持的位置。下载地址必须稳定、可配置，不能假定 `/docs`
下已经存在 Skill 文件；更新时比对远端版本与本地修改，不静默覆盖本地定制。公开
指令应包含足够的引导，但受保护 Skill 不得包含真实 Token。未经鉴权的访问不应
泄露私有内容。不同 Agent 产品的 Skill 放置路径和安装机制可以不同，不强迫一种
具体客户端布局。

首选操作方式为标准 HTTP：Skill 解释鉴权、发现 Library／Section／Book、读取、
搜索、准备本地文件、上传、幂等重试、版本条件、写后验证和错误处理。提供 Bash、
PowerShell 和 Python 等可复现示例；示例使用本地文件或流，不把内容和 Token 拼进
命令行参数。已有 CLI 与 MCP 可以继续维护兼容，但下载 Skill 和使用知识库均不应
以安装它们为前提。旧 Skill 当前写有「禁止原始 HTTP」，须在新接口完成并验证后
显式修订，不能让新旧指南相互矛盾。

## 8. 当前 Revision 的真实搜索

搜索必须是真实可用的功能，不能以模拟界面或静态示例替代。第一阶段不依赖向量
数据库、外部模型或语言词典，采用可重建的字符／词元倒排索引作为候选召回基础。
中文至少覆盖单字、双字和三字连续片段，英文和数字需要明确规范化。全文只索引每个
未删除 Page 的当前 Revision，历史内容仍由明确历史接口访问。索引属于派生状态，
创建、修订、删除、恢复、改 Tag 或校正时间时，应与权威内容保持一致或明确失败关闭。

查询输入以结构化字段表达，不接收用户拼接的 FTS／SQL 语法：

- `keywords`：零到多项字面字符串。建议以「匹配越多、越重要字段越靠前」排序，
  而不是要求每项都出现；人类界面用空格拆分已明确分开的词，不强迫中文用户先分词。
- `tags_any`：零到多项已存在的 Tag。非空时 Page 至少包含其中一个；命中多个可
  给予额外权重。Tag 名称无效时返回明确错误或建议，不静默忽略。
- `occurred_from`／`occurred_before`：可单独使用的 UTC 声明时间范围，不填即
  不限制；不要求虚构一个「无限大」时间值。
- `libraries`：管理员可选一个或多个已授权 Library；普通调用方只能选自己可读的
  Library，结果不能泄露其他 Library 的计数、排序影响或摘要。
- `limit`／游标：返回 Top K Page，含标题、归属、命中解释、准确当前 Revision 引用
  和供人预览的安全摘要；取完整文件需另行按 Page／Revision 请求。

没有关键词但有 Tag 或时间条件时仍可检索；完全空条件的浏览语义和默认排序须在接口
提案中明确。Tag 权重、标题／正文权重、同分决胜、分页游标和查询变更时的一致性
必须有确定规则。服务器可自行选择先利用倒排索引、Tag 索引还是时间索引；「先授权
与筛选，再排序」是结果语义，不是要求 SQL 固定执行顺序。Tag 列举、Tag 下 Page
列表及 Tag 管理同时提供给网页和 Agent。

旧 FTS 提案中的每 Section 最多 1,024 篇、候选最多 256 项会拒绝正常的大范围或
高频词查询，而且旧查询把词元全部按 AND 组合；这些都与本阶段预期的数千篇内容和
关键词数组相关性排序不一致，因此**不能原样接受或实施**。应修订
索引表示、候选召回与排序路径，在约 5,000 篇、每篇约 10 KiB 的代表性中英文内容
上记录索引构建、更新、冷／热查询、常见／罕见／无命中词、Tag 和时间组合、并发
与数据库体积。正常查询约一秒是性能目标，不是靠任意截断候选或阻止常见查询制造
出的假指标。仍需对异常巨大的原始请求、单项长度、响应数量与总工作量设置合理保护；
超限或超时必须显式报错，不返回看似完整的部分结果。是否使用语料相关性统计或固定
字段权重，应由代表性评估决定，不能仅凭示例固定。

## 9. 实施顺序与验收边界

1. 先确认本提案中的接口和存储未决事项，更新与之冲突的已接受决策；修订 FTS 提案
   并经独立审查后，才能开始生产索引迁移。
2. 先增加向后兼容的存储结构、备份与数据迁移验证；现有单 Markdown Page 必须可
   映射为仅含一文件的多文件 Page，旧客户端不能被无提示地破坏。
3. 再完成多 Library 权限、Tag、Page 文件快照、时间校正、软删除／恢复和非搜索
   读取，随后上线真正的倒排检索与性能回归。
4. 管理后台与 Agent Skill 只调用已实现且已测试的接口；界面不可先展示尚不存在的
   创建、搜索、恢复或重复取回 Token 功能。新增操作需覆盖权限、并发、幂等、回读、
   隐私、迁移和回退测试。
5. 使用合成数据完成跨系统 AI 接入和约定规模搜索测试；真实内容导入、真实备份
   恢复和私有部署属于单独授权的运维步骤，不由文档提交自动触发。

逐设备验收应分步记录实际入口可达性、Token 身份与 Library 权限、Skill 下载和
安装、读取、搜索、上传及写后准确回读，而不是只凭登录页打开就宣告接入完成。
分散资料的导入先只读清点来源、格式、时间和重复项，确定 Library／Section／Book
归属，再用少量非敏感样本试导入并核对 Page ID、Revision、文件清单、哈希和搜索
结果。设备名单、私有地址、资料路径、凭据和测试正文留在私有验收记录，不写入
公开仓库；任何真实资料导入仍须另行授权。

## 10. 实施前仍需明确的技术决策

- 管理 Token 首次创建的本机操作或一次性带外证明、遗失恢复，以及旧密码登录的
  兼容／回退期限；新管理身份是否接替现有 operator Token 的操作授权和审计主体。
- 管理 Token 轮换后即时撤销旧会话、重复显示 Agent Token 时的重新验证要求，
  及默认掩码、眼睛、复制操作的响应与浏览器防泄漏边界。
- Agent Token 可恢复密文的加密方式、数据库外解密材料和密钥版本／轮换、
  独立密钥备份与恢复演练、缺钥时的失败关闭，以及历史备份中已吊销凭据的处理。
- 现有不可还原 Token 的到期或主动轮换策略，以及「每身份默认一枚活动 Token」
  与当前可存在多枚凭据的兼容规则。
- 旧 Section grant 到新 Library 读／写权限的无扩权迁移，以及 `write` 与 `read`
  的关系。
- 多文件 Page 的存储方式、哈希规范、文件名规范、类型和大小配额、相对引用和
  下载预览安全边界，以及数据库备份／导出是否覆盖所有文件字节与历史。
- 声明时间公开 API 的精确单位、时间校正对 Page ID 旧时间片段的展示说明，以及
  内容相同但元数据变化时的响应结构。
- 搜索关键词组合、字段权重、Tag 加权、空查询、容量基准及索引重建失败语义。
- API 请求记录的保留期限、失败请求覆盖、访问权限和导出范围。

这些问题是实施契约的门槛，不是重新否定已经确认的产品目标。每项实现仍需明确
区分「已写入文档」「已编码」「已测试」「已合并」「已部署」与「真实数据已验收」。

# Alpha 阶段的 SQLite 备份、恢复与升级

状态：**提案中（Proposed）**

## 待决定事项与门槛

建议把本文的生命周期与安全边界作为 Alpha 阶段的设计，用于 SQLite 全库备份、恢复
到新数据槽，以及数据库结构升级。本提案优先使用 SQLite 在线备份 API 复制在线来源；
只有清单完整后才发布不可变备份包；升级期间，旧应用镜像始终与其未被改动的旧数据槽
配对。

**本提案尚未被接受。** 合并本文、加入实验性备份库或通过合成恢复演练，都不代表
真实数据部署或时间点恢复已经达到生产可用。接受本方案需要维护者公开审查并改变状态。
时间点恢复分支还会继续受阻，直到下文明确的凭据隔离及标识符/幂等信息防复用决定
得到解决。

本文定义的是可移植应用契约，不标明任何部署主机、存储路径、域名、凭据、机密值
或私有拓扑。

## 范围与术语

若干操作都使用“恢复”一词，但权限和失败方式不同。它们不得共用含义不清的命令或
就绪声明。

| 操作 | 含义 | 是否保留运行数据库状态？ | Alpha 定位 |
| --- | --- | --- | --- |
| Page Revision 恢复 | 创建一个正文源自早期 Revision 的新 Revision，再在普通变更事务中推进 Page 的当前指针。 | 是；此前历史仍保持线性且不可变。 | 已有的公开内容恢复方向，不是数据库恢复。 |
| 全库备份 | 捕获一个一致的 SQLite 快照，以及验证所需且范围有限的元数据。 | 是，准确对应捕获时刻。 | 本文提议。 |
| 全库恢复 | 验证备份包，并在不改变在线数据库的前提下将其写入新的空目标。 | 是，但必须通过准确数据库结构和语义验证。 | 本文提议。 |
| 镜像回滚 | 使用当前数据槽启动旧应用镜像。 | 不保证；数据库结构或语义可能已经前进。 | 不是数据库恢复机制。 |
| 镜像与数据槽一起回滚 | 返回旧的不可变镜像，以及它之前提供服务时使用且未被改动的准确旧数据槽。 | 仅在候选版本尚未接受持久写入前可以保证。 | 拟议的升级安全机制。 |
| 导出 | 生成所选内容和元数据在应用层可互操作的表示。 | 不一定；可能缺少凭据、审计、幂等、迁移状态和派生数据。 | 需要单独提供，不能替代备份。 |

**镜像（image）** 是不可变应用制品。**数据槽（data slot）** 是一个数据库位置，
任意时刻只归一个活动镜像世代所有。**备份包（backup bundle）** 是不可变目录，
包含一个 SQLite 快照和一份清单。**备份收据（backup receipt）** 是管理员持有的记录，
证明具名备份包已经完成并通过必需验证；它是部署门槛，不是备份载荷本身。

## 拟议的 Alpha 不变量

### 捕获与不可变备份包

1. 在线数据库通过 SQLite 复制，不直接复制打开的主数据库文件。Alpha 实现使用
   Python `sqlite3.Connection.backup()` 提供的 SQLite 在线备份 API。
2. 来源和目标使用不同的数据库连接及文件系统对象。目标必须在暂存目录中新建。
   已有文件、非空目录、来源别名、符号链接、重解析点和其他路径间接访问都按失败
   关闭处理。
3. 即使其他连接在复制期间继续写入，完成的 SQLite 快照仍表示一个一致的来源状态。
   实现必须限制忙碌等待、运行时间和资源用量；无限重启的复制属于失败，不是进展。
4. 快照关闭并通过验证后才能发布。验证以只读查询模式打开快照，不得修复、迁移、
   vacuum、规范化或以其他方式改变候选制品。
5. 备份包使用严格、带版本的清单，包含有大小上限的字段、规范编码、准确数据库内容
   摘要、准确 Alembic head、验证契约版本、规范 UTC 完成时间和验证结果。未知字段、
   重复键、非有限数字、格式错误时间戳和非规范编码都会被拒绝。
6. 清单最后写入。只有数据库和清单在平台支持所需同步的情况下都已持久化，才能把
   暂存目录重命名为最终名称。读取方把缺少清单、清单无效或非最终清单的目录视为
   未发布备份包。
7. 目录重命名和最后写清单可以防止协作式读取方接受不完整备份包，但无法为所有文件
   系统、对象存储或断电边界提供通用的多文件原子性保证。存储适配器必须记录并测试
   自身发布语义。
8. 发布后，数据库和清单都不得原地修改。新的验证结果或存储转换会创建新备份包身份。
   恢复绝不覆盖已发布备份。

SQLite 文档说明，在线备份 API 会生成快照，并且只在每个读取步骤短暂锁定在线来源。
Python 3.13 通过 `Connection.backup()` 暴露该 API，并支持其他客户端同时访问数据库。
SQLite 还警告，直接复制活动数据库文件可能产生混合状态，而且 WAL 或热日志也属于
数据库状态。因此 Alpha 契约禁止原始在线文件复制。

### 完整性、真实性与机密性

只有清单本身可信时，清单摘要才能检测意外截断、替换或损坏。能够同时替换数据库和
清单的攻击者可以计算新的普通摘要。“最后写清单”是完成协议，不是真实性证明；创建
时间戳也不是新鲜度或防回滚证明。

因此 Alpha 备份包格式有两个明确的信任边界：

- 当所在存储已经可信时，本地完整性验证可以依赖清单中的密码学摘要；
- 信任边界外的存储成为生产恢复来源前，需要使用受到独立保护的 MAC、签名或等价的
  认证目录。

准确的真实性机制、密钥保管、保留策略和防回滚目录仍是开放问题。在这些决定被接受
前，来自不可信或可重放位置的备份包不能用于自动恢复。

全库备份具有与在线数据库相同的机密性和管理性擦除影响，其中包含内容、历史、
Source、调用方和授权记录、凭据校验值、审计事件及幂等响应。静态加密、访问策略、
复制、保留、销毁和支持处理至少要与在线数据一样严格。校验值虽不是明文 bearer
令牌，仍属于安全敏感信息。日志、收据和错误消息不得包含文档正文、凭据材料，或会
暴露管理员专用基础设施的清单字段。

### 准确数据库结构兼容性与语义验证

备份记录一个准确的 Alembic head。普通恢复验证器只接受它自身可验证的准确数据库
结构 head，不会猜测迁移路径、让旧镜像处理较新的数据，或悄然升级恢复后的数据库。

除非所有适用检查都通过，否则验证必须按失败关闭处理，包括：

- `PRAGMA integrity_check` 准确返回 `ok`，且 `PRAGMA foreign_key_check` 不返回行；
- 必需的表、索引和关键触发器与准确的预期数据库结构匹配，而不只是拥有相同 Alembic
  版本字符串；
- 每个 Page 当前指针都指向同一 Page 的准确 Revision，Revision 编号从 1 起连续，
  且不存在未完成的追加保护标记；
- 已存内容大小与摘要和 Revision 字节一致，每个 Source 都关联到准确 Page 和 Revision；
- 规范及别名标识符保留项仍只附属于一个 Page，冲突计数器不低于永久保留项所暗示的
  高水位；
- 初始化、调用方、凭据轮换、授权和审计关系在内部一致，不存在凭据环或不可能的
  生命周期；
- 每份持久幂等响应都可解析，并与已存方法、路由、Page、Revision、引用、Location
  和实体标签一致；
- 已接受的派生状态版本必须兼容且有效，否则在确定性重建成功前应声明不可用。

实现可以增加更严格检查，但不能削弱上述不变量。验证契约必须带版本，使收据能够
说明实际证明了什么。

### 只恢复到新的空目标

恢复把经过验证的快照写入新的空数据槽，绝不覆盖在线数据库、旧数据槽或其他备份。
恢复目标遵循与备份相同的别名和路径间接访问检查。

写入后，再从目标位置验证恢复数据库。只有复制字节、准确数据库结构和语义检查都
符合备份包契约，恢复才成功。成功只表示“经过验证的非活动数据槽”，不授权流量、
迁移或凭据使用。

## 无损升级工作流

Alpha 升级路径采用复制后提升，不是原地迁移后只回滚镜像：

1. 确认当前提供服务的组合：旧不可变镜像与旧数据槽。
2. 完成全库备份及验证。
3. 持久化迁移前备份收据，其中包含不可变备份包身份、清单摘要、来源数据库结构
   head、验证契约版本和完成结果。部署进程失败后，控制器仍必须能读取该收据。
4. 把备份包恢复到全新的候选数据槽。旧数据槽保持不变且仍归旧镜像所有。
5. 只对候选数据槽运行候选镜像的迁移。
6. 候选与普通写入隔离时，对其执行准确数据库结构验证、应用就绪检查和合成只读探针。
7. 把服务从旧组合切换到候选镜像与数据槽组合。
8. 记录候选是否已经接受第一次持久写入。

迁移前收据是必需条件。仅仅存在的文件、未经验证的摘要，或指向不同来源字节的旧
成功收据，都不能满足门槛。

当备份时点是为切换选择的最新已提交权威状态，且旧组合接受的写入没有被遗漏时，
该流程属于**无损升级副本**。部署可能需要短暂暂停写入或采用等价的最终同步步骤；
具体可用性技术属于实现决定，但仍必须证明没有遗漏写入这一不变量。

### 配对与回滚边界

旧镜像只能与准确且未被改动的旧数据槽一起回滚。即使迁移降级测试通过，也绝不能把
旧镜像自动配给已经运行迁移的候选数据槽。只要旧组合仍有资格回滚，它就保持隔离且
不可变。

候选接受持久写入前，健康或切换检查失败时可以停止候选并返回旧组合。候选接受任何
持久写入后，禁止自动回滚到旧组合：旧数据槽不含该写入，继续使用会悄然分叉历史、
恢复旧安全状态，或在不同事实下重放幂等变更。此时安全选择只有向前修复、在新数据槽
中进行经过审查的协调，或执行明确授权的灾难恢复流程。决定完成前保留两个数据槽。

## 失败状态机

```text
SERVING_OLD_PAIR
  -> CAPTURING_BACKUP
  -> VERIFIED_BACKUP_RECEIPT
  -> RESTORED_FRESH_CANDIDATE_SLOT
  -> MIGRATED_AND_VALIDATED_CANDIDATE
  -> CANDIDATE_CUTOVER_NO_WRITES
  -> CANDIDATE_HAS_DURABLE_WRITES
```

- `CAPTURING_BACKUP` 失败时不发布备份包，旧组合继续服务。
- 在 `VERIFIED_BACKUP_RECEIPT` 后、切换前失败时，只销毁或隔离候选数据槽；旧组合
  仍是权威来源。
- `CANDIDATE_CUTOVER_NO_WRITES` 阶段失败时，证明候选没有接受持久写入后可以返回
  旧组合。
- `CANDIDATE_HAS_DURABLE_WRITES` 阶段失败时停止自动回滚。保留两个数据槽、防止
  双写，并要求审查后的向前恢复或协调。
- 控制器本地进程丢失不会抹除持久状态。重启后必须从已认证收据和明确数据槽所有权
  推断阶段，不能猜测当前镜像标签。
- 阶段未知、收据缺失、数据槽所有者不明确或发布不完整时，按失败关闭处理，并要求
  管理员审查。

每次状态转换必须幂等，或能检测到另一个操作已经在进行。任何失败路径都不得删除
最后一份经过验证的备份，或最后一个已知良好的镜像与数据槽组合。

## 时间点恢复是独立安全事件

**时间点恢复（PITR）** 会有意选择早于最新提交状态的快照，不同于上述无损升级副本。
缺失时间段可能包含内容变更、Page ID 保留、幂等响应、调用方或授权变化、凭据轮换
和吊销，以及审计事件。

恢复的旧快照必须进入 `PITR_QUARANTINED`，不能接收 Agent 或公开流量，也没有普通
写入权限。只有以下各项都实现并得到证明后，才可提供服务：

1. **凭据与调用方隔离。** 把所有恢复出的调用方、凭据、授权和初始化权限视为不可信
   历史状态。网络暴露前，恢复流程必须禁用或替换这些状态，并证明恢复点之前或之后
   有效的凭据不会意外复活。
2. **操作日志隔离。** 恢复边界两侧的客户端或外部操作日志都不能自动重放，必须依据
   选定的权威时间线进行协调。
3. **游标隔离。** 替换分页游标签名材料，使针对任一废弃状态签发的游标都不能在恢复
   状态上重放。
4. **外部不连续记录。** 在恢复数据库之外的仅追加记录中，标明所选备份、废弃区间、
   新旧状态身份、验证结果和恢复授权。记录不含机密或文档正文，也不会随数据库回滚。
5. **标识符与幂等信息防复用。** 恢复点后创建的 Page 标识符保留项、冲突计数器
   高水位和幂等键摘要必须保留，而且不得重新用于其他 Page、Revision、调用方、请求
   或响应。

第五项目前没有已接受机制。未来可以使用独立持久的单调保留台账，或经过审查地合并
废弃状态中的高水位安全元数据；两者都有隐私、真实性和可用性权衡，本提案不作选择。
因此，在本提案仍为 Proposed 且防复用决定未解决时，旧 PITR 快照可以用于检查或
构建经审查的恢复候选，但不得提供写入服务。

## 威胁模型与安全影响

Alpha 设计至少必须处理以下失败与攻击类别：

- 在线原始文件复制遗漏 WAL 或热日志，或与之不匹配；
- 崩溃、磁盘写满、取消或断电留下部分备份包；
- 来源/目标别名、路径遍历、符号链接、硬链接、重解析点、挂载或竞态攻击覆盖在线
  数据或越出允许根目录；
- 覆盖已有数据库，或恢复到仍归运行中进程所有的数据槽；
- 损坏数据库因损坏字节被一致捕获而通过文件摘要；
- 伪造清单、重放备份包或回滚已认证目录；
- 伪造数据库结构版本以隐藏缺失约束、索引或触发器；
- 恶意超大清单、数据库文件、行值、验证结果集或无界备份重试；
- 备份泄漏、不安全的临时权限、含机密日志，或管理性擦除后遗留副本；
- 数据库结构迁移后只回滚镜像；
- 数据槽切换时双写，或崩溃后数据槽所有权不明确；
- 自动回滚后悄然丢失候选写入；
- PITR 后恢复已吊销的凭据、调用方或授权；
- 重放恢复后的客户端日志、幂等键或旧游标；
- 复用或重新绑定永久保留项已经丢失的 Page ID；
- 恢复后的审计历史看似连续，却缺失废弃区间的外部事件。

摘要验证与 SQLite 完整性检查互为补充：前者回答字节是否与可信清单相符，后者回答
SQLite 能否验证数据库结构不变量。两者都不能证明快照足够新、已经授权、不含恶意但
有效的行，或可以安全激活。

跨保留备份的管理性擦除仍是开放的公开设计问题。实现中的任何保留声明都不得暗示
不可变备份优先于法律或管理员擦除要求。

## 验收测试

验收需要为以下所有适用事项提供公开、合成且可复现的证据。

### 备份包

- 在并发提交期间分别从 rollback-journal 和 WAL 数据库创建备份；每个被接受的备份包
  都是一个一致的 SQLite 快照。
- 证明来源/目标直接同一，以及通过链接或平台路径间接访问形成的别名，都会在目标被
  修改前失败。
- 在每个发布步骤注入取消、忙碌耗尽、磁盘写满、短写和进程终止。任何不完整目录都
  不能被当作最终备份包接受。
- 拒绝已有目标、缺失或过早写入的清单、截断数据库、错误摘要、未知或重复清单字段、
  非规范 JSON、非有限数字、格式错误时间戳及超大输入。
- 演示替换清单能够绕过普通摘要，并在声称生产可信前证明独立认证目录可以检测替换
  与重放。
- 确认暂存和发布时采用严格权限，并证明日志与收据不含内容、凭据材料或私有基础
  设施值。

### 验证与恢复

- 测试完整性和外键失败，以及每项 Page/Revision/Source、标识符/计数器、身份验证/
  审计和幂等语义不变量。
- 拒绝 Alembic 版本正确但缺少或改变表、索引、约束或关键触发器的数据库。
- 只恢复到新的空数据槽，验证写入后的目标，并证明失败绝不改变来源、在线数据槽或
  备份包。
- 在每个受支持操作系统和生产 OCI 文件系统/UID 模型中，只使用合成数据验证恢复。
- 证明准确数据库结构恢复不会运行迁移，而且升级迁移只在候选数据槽通过验证恢复后
  运行。

### 升级与回滚

- 如果准确的迁移前备份收据缺失、无效、在需要时未认证，或指向不同来源字节，必须
  阻止迁移。
- 在每次状态转换前后注入失败，恢复时不得产生双写或丢失旧组合。
- 只用旧数据槽冷启动旧镜像，只用候选数据槽冷启动候选镜像；不得交叉配对。
- 演示候选写入前失败能够安全返回旧组合。
- 演示第一次持久候选写入会改变状态，使所有自动回滚路径按失败关闭处理。
- 根据持久收据和数据槽所有权证明控制器重启行为，包括需要人工审查的歧义状态测试。

### 时间点恢复

- 恢复一个早于调用方创建、凭据轮换与吊销、授权变化、幂等变更、Page ID 冲突和
  审计事件的快照。
- 证明恢复出的凭据/调用方/授权，以及新旧操作日志都保持隔离；任何读取流量前轮换
  游标签名材料。
- 数据库回滚时追加并保留外部不连续记录。
- 证明快照后的 Page ID、冲突序号和幂等键不会被复用或重新绑定。
- 防复用证据缺失或恢复区间含糊时，恢复数据槽必须保持不服务。

PITR 测试组在缺失的公开决定和持久状态实现前无法通过。Alpha 真实数据就绪性不会
豁免这组测试。

## 考虑过的替代方案

### 停止服务后复制文件

所有日志状态保持完整时，可以安全复制完全静止的数据库。这在另行证明停止和文件
系统契约后是有效的管理员技术，但不是默认在线备份 API。无法证明静止，或没有配套
WAL/热日志，都可能破坏副本。

### `VACUUM INTO`

SQLite 把 `VACUUM INTO` 记录为另一种一致的在线备份机制。它会生成紧凑文件并清除
已删除空闲页中的内容，但会使用更多 CPU，不能在其连接存在打开的事务时运行，可能
改变无键 rowid，而且中断的输出可能不完整。增量在线备份 API 更符合 Alpha 的在线
复制和明确验证路径。`VACUUM INTO` 仍可以作为未来的存储转换，用于创建新备份包，
而不是重写已有备份包。

### SQL 转储或应用导出

SQL 转储便于检查，应用导出可以跨版本移植，但两者都不会自动保留每项运行不变量、
SQLite 数据库结构对象、二进制值、安全记录或幂等响应。它们需要独立的往返契约，
仍是互补工具。

### 原地迁移并只回滚镜像

这种方式占用存储更少，但会要求每次迁移在部分失败后都向后兼容。当前启动时迁移和
镜像回滚形式本身不能证明数据库可恢复。为满足真实数据就绪性，本提案拒绝该方案，
选择成对数据槽。

### 文件系统或卷快照

存储快照可以快速且节省空间，但必须针对每个后端证明应用静止、SQLite/WAL 一致性、
持久性、访问控制和恢复语义。它可以成为另一种备份适配器，但不能削弱备份包或验证
契约。

### 连续 WAL 归档

连续归档可以减少数据丢失，但恢复到旧时点会面临上述凭据、审计、游标、标识符和
幂等风险。PITR 安全状态和防复用设计被接受前，该方案继续推迟。

## 依赖与实现顺序

```text
public acceptance of this proposal
  -> bounded backup/manifest/validation core
    -> local operator backup and exact-schema restore commands
    -> OCI UID/filesystem restore drill
    -> authenticated backup receipt and pre-migration deployment gate
      -> fresh data-slot migration and validation
      -> paired image-and-slot cutover controller
      -> real-data deployment readiness review

public PITR quarantine decision
  -> external discontinuity record
  -> credential/caller/journal/cursor quarantine implementation
  -> accepted Page-ID/collision/idempotency anti-reuse mechanism
    -> destructive and adversarial PITR drill
    -> separate PITR activation decision
```

可以在这些门槛后开发原型代码，但下游组件不得声称上游 Proposed 决定已经接受。
备份存储、版本发布、机密和私有部署仍是必须串行执行的管理员职责。

## 开放问题

接受通用备份和无损升级路径前，仍需回答：

- 第一个受支持的 wire format 应采用哪套规范的 manifest schema，以及哪个验证契约版本？
- 对存放在可信本地边界外的备份，哪种认证目录、MAC 或签名机制足够可移植，又如何
  防止重放？
- 不可变备份包适用什么保留、轮换、安全擦除和管理性擦除策略？
- 支持的最大数据库大小、备份时长、忙碌重试预算、预留空间和验证资源预算是多少？
- 发布备份包和切换数据槽需要哪些跨平台文件系统操作及目录同步保证？
- 控制器生成切换副本时，如何证明写入静止或最终同步？
- 哪个持久事件标志候选第一次接受写入，重启后的控制器又如何在不信任可变本地进程
  状态的情况下验证？
- 哪些派生投影按字节验证，哪些在就绪前重建，哪些在恢复后有意保持不可用？
- 例外管理性擦除后，如何查找并擦除备份？

PITR 还需要另行接受以下答案：

- 如何在不只依赖已回滚数据库的情况下，使恢复出的凭据、调用方、授权和初始化权限
  失效？
- 外部不连续记录存放在哪里、由谁授权，如何保护真实性和单调性？
- 哪种 Page ID 保留项与冲突计数器高水位台账可以防止跨废弃未来时间线复用？
- 如何协调持久幂等键和操作日志，同时不重放或重新分配已接受操作？
- 上述安全机制存在后，可以支持何种恢复点目标？

在通用问题被接受并通过测试前，全库工具仍是实验性功能。所有 PITR 问题被接受并
通过测试前，旧快照只能处于隔离状态。
